# Grok Bot 多 bot 团队搭建指南

为用户设计一支 Grok Bot 多 bot 团队时使用：从确定用户类型，到写出每个 bot 的提示词、共享文件夹约定、派活/回报模板、验收标准和例行任务，最后交付一套可以直接照着配置的方案。

## 基本前提

- Grok Bot 可以同时运行多个 bot。每个 bot 有自己的对话、描述提示词（人设）、记忆、定时例行任务和连接的工具（如 Gmail、Calendar、Slack、GitHub、X、Notion）。
- 所有 bot 共用同一台云电脑（文件共享），但各自有独立的桌面和浏览器；bot 之间通过消息协作。
- 因此团队协作靠两样东西：**消息**（派活、回报）和**共享文件夹**（交付物）。
- 只推荐用户已连接或可连接的工具；不要编造产品界面的菜单路径，涉及配置步骤时用"创建 bot → 粘贴提示词为描述 → 连接工具 → 设置例行任务"这样的通用说法。

## 第 1 步：确定用户类型和目标

先弄清楚四件事（缺什么就问）：

1. **用户是谁**：职业/角色、日常工作中最耗时的环节。
2. **核心目标**：想省下哪部分时间，或想把什么做得更稳定（例如"不漏跟进""每周按时出内容"）。
3. **可用工具**：已在用哪些服务（Gmail、Calendar、Slack、GitHub、X、Notion 等），数据以什么形式存在（邮件、日历、导出文件）。
4. **红线**：哪些事必须本人确认（对外发送、付款、交易、删除、合同承诺等）。

能对上附录中的某个场景时，以它为起点改造；对不上时，按"输入 → 加工 → 产出 → 对外"拆出用户的工作流。

## 第 2 步：设计团队结构（1 个主管 + 3–4 个专员）

推荐模式：

```
你把需求发给「主管」
→ 主管拆解任务，发消息派给专员（写明交付物与验收标准）
→ 专员完成后存到 /workspace/shared/<名称>/ 并把路径回报主管
→ 主管打开文件核对验收标准
→ 合格后交付给你
```

设计要点：

- **主管**是用户唯一的日常入口：拆解、派活、验收、交付、维护看板/排期；连接日程和沟通类工具（Gmail、Calendar、Slack、Notion）。主管不自己埋头做专员的活。
- **专员**按工作流环节划分，每个只负责一件事（研究 / 写作 / 数据 / 对外草稿 / 审查等），工具只连它需要的。
- 3–4 个专员通常足够；更多会增加主管的协调成本。
- "做"和"查"分开（如编码与审查、写作与核实），形成第二双眼睛。
- 任何涉及对外的专员（邮件、帖子、消息）都只出草稿。

为每个 bot 写下：名称、emoji（可选）、一句话职责、建议连接的工具、例行任务、提示词。

## 第 3 步：用 7 个部分写提示词

bot 的描述提示词决定它"是谁、做什么、怎么做"。每个 bot 的提示词都包含以下 7 部分：

| # | 部分 | 写什么 | 示例 |
|---|------|--------|------|
| ① | 角色定位 | 一句话：它是谁、服务谁、核心目标 | 你是「选题研究员」，为一位科技类视频博主寻找有传播潜力的选题。 |
| ② | 任务范围与边界 | 负责的事 + 明确不做的事（不代发、不付款、不发布） | 只做研究与建议；不发帖、不回复他人。 |
| ③ | 输出格式 | 文件类型、结构、字数、表格列、命名规则、保存路径 | Markdown 表格：选题 \| 依据链接 \| 热度判断 \| 建议角度。 |
| ④ | 语气 | 对用户/对外的写作风格 | 结论先行，口语化但专业。 |
| ⑤ | 工作流程 | 按步骤写，最后一步是自检 | 1. 扫描 → 2. 去重 → 3. 打分 → 4. 自检 → 5. 存档并回报。 |
| ⑥ | 何时询问用户 | 对外发送、花钱、删除、信息不足、存在多种理解时 | 任何对外发送的内容，先给草稿，等用户确认。 |
| ⑦ | 与其他 bot 的协作 | 主管是谁、和谁配合、文件存哪里、完成后回报什么 | 成果存到 /workspace/shared/creator/research/，完成后把路径和摘要发给「内容主管」。 |

### 提示词骨架（可直接套用）

```
你是「<bot 名称>」，<服务对象>的<角色>，目标是<核心目标>。

## 任务范围
- ...

## 边界（不要做）
- ...

## 工作流程
1. ...
n. 自检：...

## 输出格式
- ...

## 语气
...

## 何时先询问
- ...
- 任何对外发送、发布、付款、删除等不可逆操作之前

## 与其他 bot 的协作
（见下方主管版 / 专员版）
```

**主管版协作段**必须包含：

- 团队成员列表：每个专员的名称、职责、产出目录。
- 派活规则：
  1. 用消息派活，每条消息必须包含：任务、背景、交付物、验收标准、截止时间、保存路径。
  2. 一条消息只派一个任务；需要多人配合时分别派活，并说明先后依赖。
  3. 专员回报文件路径后，先打开文件，逐条核对验收标准，再决定是否交付。
  4. 不合格时退回，写明哪一条未达标、如何修改；两轮仍不达标，向用户说明情况。
  5. 交付给用户时附：一句话结论、文件路径、要点摘要、需要用户决定的事项。
  6. 自己的汇总与交付文件保存在主管自己的目录。

**专员版协作段**必须包含：

1. 主管是谁；按主管消息中的交付物与验收标准工作，信息不足先问主管，不要猜。
2. 成果保存到自己的目录，文件名 `YYYY-MM-DD-简短任务名`。
3. 完成后回消息：文件路径、3 行以内摘要、逐条自检结果、未解决的问题。
4. 需要别人的产出时从对应共享文件夹读取，不修改别人的文件。
5. 用户直接找它时可以直接回答，但重要产出同样存档并告知主管。

写作提醒：

- 边界写成具体动作（"不发送邮件，只创建草稿"），不要写成空泛的"注意安全"。
- 不编造事实、数据、引用；拿不到的写"未知"或标注【待核实】。
- 用户确认过的长期偏好（固定格式、常用语气、客户名单、底线规则）可以让 bot 记入记忆，但核心规则仍写在提示词里。

## 第 4 步：共享文件夹约定

每个团队一个根目录 `/workspace/shared/<名称>/`（`<名称>` 用简短英文 id，如 creator、sales）：

```
/workspace/shared/<名称>/
├── lead/            ← 主管的汇总与交付
├── <专员 id>/       ← 每个专员一个子文件夹
├── data/            ← 用户放入的原始资料/导出文件（只读，按需设置）
├── <客户或项目>/    ← 需要时：每个客户/项目一个子文件夹
└── README.md        ← 主管维护：目录说明、命名规则、当前进行中的任务
```

规则：

- 文件名统一为 `YYYY-MM-DD-简短任务名`，便于按日期查找。
- 每个 bot 只写自己的子文件夹，读取别人的产出但不修改。
- 原始资料只读，处理结果另存新文件。
- 依赖外部系统数据（店铺后台、CRM、券商等）时，约定由用户按固定文件名把导出文件放进 `data/`，bot 不登录这些系统。

## 第 5 步：派活与回报模板

**派活消息（主管 → 专员）**

```
@<专员名> 新任务（来自「<主管名>」）

【任务】...
【背景】...（相关文件路径）
【交付物】
- ...
【验收标准】
1. ...（可检查、可量化）
【截止时间】...
【保存路径】/workspace/shared/<名称>/<专员 id>/（文件名：YYYY-MM-DD-简短任务名）
【回报方式】完成后回复我：文件路径 + 3 行摘要 + 逐条自检结果 + 未解决问题。信息不足请先提问，不要猜测。
```

**回报消息（专员 → 主管）**

```
@<主管名> 任务已完成：「<任务>」

【文件】/workspace/shared/<名称>/<专员 id>/YYYY-MM-DD-任务名.md
【摘要】（3 行以内）
【自检】
1. <验收标准 1> —— ✅ 已满足 / ⚠️ 部分满足（原因）
【未解决问题】（如无写"无"）
```

验收标准要写成能逐条打勾的条件（数量、范围、格式、来源、"不出现 X"），避免"写得好一点"这类无法验收的描述。

## 第 6 步：验收检查（主管交付前）

通用清单，再按场景补 2–4 条专属项：

- ☑️ 文件存在，路径与派活消息一致
- ☑️ 逐条对照验收标准，未满足项写明原因
- ☑️ 事实、数字有来源，或已标注【待核实】
- ☑️ 对外内容（邮件、帖子、消息）仍是草稿，没有被发送或发布
- ☑️ 没有越过用户设定的红线（价格、付款、交易、删除、承诺）
- ☑️ 不合格时附具体意见退回；两轮仍不达标，向用户说明情况

## 第 7 步：例行任务（routines）

- 主管：每日晨报（今日日程、待决定事项 ≤3 项、各专员进度）+ 每周计划/周报。
- 专员：在主管晨报**之前**跑完自己的例行任务（如 07:30 收集素材 → 08:30 主管汇总），让晨报有新鲜输入。
- 事件驱动类：按日历提前准备（如"每天 18:00 检查明天的会议并出简报"）。
- 数据类：固定时间读取 `data/` 中最新文件；文件缺失或过期时告知主管，不推测。
- 时间均为示例，提醒用户按自己的时区和作息调整。

## 第 8 步：交付给用户的方案格式

给每个场景输出：

1. 团队概览：适合谁、主管 + 专员结构、协作流程（可附结构图）。
2. 每个 bot：名称、职责、建议连接的工具、例行任务、完整可复制的提示词。
3. 一个具体的派活消息示例 + 对应的回报模板。
4. 共享文件夹目录树。
5. 验收检查清单。
6. 3–4 条管理技巧（例如"只在关键节点介入""把偏好写进记忆""草稿制度"）。
7. 安全说明：对外发送、付款、交易、删除前一律先出草稿、由用户确认；投资类内容只做信息整理，不构成投资建议。

## 自检（交付方案前）

- [ ] 每个 bot 的提示词 7 个部分齐全，主管写明团队成员和派活规则
- [ ] 每个专员有独立产出目录，路径与目录树一致
- [ ] 所有对外动作都是"草稿 + 用户确认"
- [ ] 工具只来自用户实际可用的连接，没有编造菜单路径
- [ ] 例行任务时间先后合理（专员先于主管汇总）
- [ ] 派活示例的验收标准可逐条检查

## 附录：8 个场景速查

### 1. 内容创作者（creator）
- **内容主管**（主管）：接收内容需求，拆解派活，维护排期，验收后交付终稿和发布建议。
- **选题研究员**：追踪 X 热点和同类创作者，产出带依据的选题清单。
- **脚本撰稿人**：按已确认选题写长文、视频脚本、标题和封面文案。
- **分发运营**：改写多平台版本，汇总帖子表现，筛选合作邮件并起草回复。

### 2. AI Builder（builder）
- **技术主管**（主管）：把需求和 bug 拆成任务，排优先级，派活验收，汇报进展与风险。
- **编码工程师**：在云电脑上实现功能、修 bug、跑测试，提交分支和 PR。
- **代码审查员**：审查 PR 的正确性与安全性，补测试，给出审查意见。
- **AI 研究员**：跟踪模型、框架、论文动态，做技术选型对比和小验证。
- **文档与发布**：维护 README，生成 changelog，起草发布帖子。

### 3. 小企业主（smb）
- **总经理助理**（主管）：统一入口，整理日程和重要邮件，每日晨报，分派任务。
- **客服专员**：分类客户咨询邮件，按 FAQ 起草回复，维护问题库。
- **财务助理**：整理发票账单，维护收支表，提醒应收应付。
- **营销助理**：策划促销，撰写社媒和邮件营销文案，关注同行动态。

### 4. 自由职业者/咨询师（freelancer）
- **业务主管**（主管）：管理客户、项目和日程，确保按时交付、按时收款。
- **拓客助理**：研究潜在客户，写个性化外联草稿，跟进未回复线索。
- **交付助理**：起草方案、报告、演示大纲，整理会议纪要与行动项。
- **账务助理**：起草报价单和发票，追踪付款，起草催款邮件。

### 5. 电商卖家（ecom）
- **店铺主管**（主管）：统筹选品、上新、客服与数据，每日经营简报。
- **选品分析师**：研究竞品价格、新品和趋势，评估候选商品。
- **商品文案**：撰写标题、卖点、详情页和多语言版本。
- **客服专员**：分类售后邮件，起草回复，汇总高频问题。
- **数据分析员**：处理放入共享文件夹的订单、流量导出，生成日报和专题分析。

### 6. 学生/研究者（research）
- **研究主管**（主管）：拆分课题阶段，管理截止日期和每周计划。
- **文献研究员**：检索筛选文献，写结构化摘要，维护文献表。
- **写作助理**：给出结构、逻辑、语言和引用格式建议（只给建议，不代写）。
- **数据分析员**：清洗数据、统计分析、作图，保存可复现代码。

### 7. 投资者/交易员（invest）
- **投研主管**（主管）：统筹情报、研究、复盘，输出投研简报（不执行、不建议具体下单）。
- **市场情报员**：监控 X 和新闻中与观察清单相关的动态。
- **研究分析师**：读公开财报，建财务表与同业对比，写研究笔记。
- **风控复盘员**：根据用户放入的交易记录复盘，检查是否遵守用户自定规则。

### 8. 销售/市场营销（sales）
- **销售主管**（主管）：管理客户名单和单子看板，统筹会前准备、跟进和 pipeline 复盘。
- **客户研究员**：研究客户公司、关键人和动态，整理客户档案与切入话题。
- **会议参谋**：准备会议简报、提问清单、异议应对和谈判方案。
- **跟进助理**：整理会议纪要，起草跟进邮件和 Slack 消息草稿，提醒久未跟进的客户。
- **管道分析员**：复盘 pipeline：阶段分布、停滞单、赢单率与推进优先级。
